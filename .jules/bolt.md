## 2025-10-07 - Missing Compound Indexes for Multi-Tenant Stats Collection
**Learning:** The database layer's `get_client_layer_stats` function performs 5 separate `SELECT COUNT(*), MAX(timestamp)` queries (one for each layer) across large tables to aggregate statistics for a specific client within a tenant/project. These tables lack compound indexes covering `(tenant, project_id, client_id)`, resulting in slow linear scans, which is an identified bottleneck specific to this codebase's multi-tenant architecture. Furthermore, the queries can be optimized by replacing the N+1 pattern with a single batched `UNION ALL` query.
**Action:** Always verify if multi-tenant data access paths utilize appropriate compound indexes (`tenant`, `project_id`, `...`). Add compound indexes `idx_{table}_tpc` on `(tenant, project_id, client_id)` for memory layer tables to optimize statistical aggregations and client-specific filtering, and batch aggregate queries where possible.
