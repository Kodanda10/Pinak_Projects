## 2025-03-01 - Add Composite Indexes for Multi-Tenant Queries
**Learning:** In the `memory_service` database schema, several large tables (`logs_access`, `memory_quarantine`, `clients_registry`, `logs_agents`, `logs_client_issues`) are frequently queried by `tenant` and `project_id` combined with another field like `ts` or `status` (e.g. `list_access_events`, `list_quarantine`). Because queries routinely filter by `(tenant, project_id, ...)`, single-column indexes on `ts` or `status` are not enough to prevent full table scans when tenant-level filtering is applied. Adding composite indexes `(tenant, project_id, ...)` avoids O(N) linear scans per tenant and speeds up these list endpoints significantly (e.g., from ~1.05s down to ~0.08s for 100k rows in a benchmark).
**Action:** Always check the query patterns on multi-tenant tables. If queries frequently filter on `tenant`, `project_id`, and order or filter by another column, add a composite index on those columns rather than relying solely on single-column indexes.
