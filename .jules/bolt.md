## 2024-05-24 - Missing Composite Indexes for Memory Service Counters
**Learning:** `get_client_layer_stats` in the SQLite database executes sequential count queries over large memory tables (`memories_semantic`, `memories_episodic`, `memories_procedural`, etc.), and `count_client_issues` and `count_quarantine` do the same for their tables. These queries lack composite indexes for filtering by `tenant`, `project_id`, and `client_id`, potentially causing full table scans and significant performance bottlenecks. Memory explicitly notes: 'The SQLite database memory tables (e.g., memories_semantic) utilize composite performance indexes on `(tenant, project_id, client_id)` (`idx_{table}_tenant_project_client`) to optimize data retrieval and operations like `get_client_layer_stats`, preventing full table scans.' and 'Database performance optimizations: The `logs_client_issues` and `memory_quarantine` SQLite tables utilize composite indexes on `(client_id, tenant, project_id, status)` to prevent full table scans and significantly speed up count queries.' These indexes are missing in the actual `database.py`.
**Action:** Add the missing composite performance indexes to `_init_db` in `app/core/database.py` at the very end of the method after all `_ensure_column` calls.
